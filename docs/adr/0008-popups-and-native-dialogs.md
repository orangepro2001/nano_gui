# ADR 0008：弹出层自绘并复刻原生行为；系统级功能用原生实现

**状态**：已采纳

## 背景
菜单、下拉列表、提示框需要与主题一致的外观，同时桌面用户对其行为（键盘导航、延迟、越界翻转）有肌肉记忆。系统原生的 `HMENU`、tooltip 控件无法与自绘主题统一，深色模式下尤其割裂。

## 决策
- **弹出层自绘**：菜单、右键菜单、下拉列表、提示框、自动完成列表由框架绘制，每个弹出层是一个**独立的无边框顶层窗口**（Win32：`WS_POPUP` + `WS_EX_TOOLWINDOW | WS_EX_NOACTIVATE`，以宿主窗口为 owner），可以超出宿主窗口边界。
- **行为复刻原生**，逐条写入控件规范并验收：键盘导航与助记符、子菜单展开/收起延迟（读 `SPI_GETMENUSHOWDELAY`）、屏幕边缘翻转与多显示器工作区裁剪、点击外部/失去激活/Esc 关闭、不抢占宿主窗口的激活状态、系统阴影、菜单动画遵循系统"显示动画"设置。
- **以下功能直接使用系统原生实现**，不自绘：
  - 文件打开/保存、文件夹选择（`IFileDialog`）
  - 颜色、字体选择对话框
  - 消息框的系统级变体（`TaskDialog`）——框架另提供主题内的自绘对话框供应用内使用
  - 托盘图标与通知
  - 剪贴板、OLE 拖放
  - 窗口标题栏与边框（使用系统非客户区，通过 DWM 属性适配深色与边框色；不自绘标题栏）
  - 输入法候选窗（由系统绘制，框架只报告光标位置）
- 模态对话框是普通顶层窗口（有系统标题栏），其客户区由框架绘制。

## 后果
- 外观统一，行为与原生一致；代价是每种弹出层的行为都要按规范逐条实现与验证。
- 多窗口、多 GL 上下文、跨窗口的输入捕获与焦点管理成为框架的必备能力（见 03、08）。
- 不自绘标题栏意味着无法在标题栏内放置自定义控件；换来的是贴靠布局、系统菜单、无障碍、未来系统更新的零成本兼容。
- GLFW 后端的弹出层退化为宿主窗口内的覆盖层（见 03 降级矩阵）。

## 被否方案
- **系统原生菜单/提示**：外观无法统一。
- **全部在窗口内自绘**：弹出层不能越出窗口，小窗口下不可用。
- **自绘标题栏**：与"克制性定制"相悖，且边角行为极多。
