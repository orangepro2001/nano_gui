# ADR 0005：受控即时模式，辅以有限的保留状态

**状态**：已采纳

## 背景
纯保留模式（控件树 + 属性 + 事件回调）状态同步繁琐、样板多；纯即时模式（每帧无条件重跑、状态全在应用）写法简洁但持续耗电、难以承载文本编辑与大列表这类需要内部缓存的控件。需要取两者之长。

## 决策
- **声明方式是即时的**：应用提供构建函数，在其中按顺序调用控件 API（如 `w.button(ui, @src(), "确定", .{})`）并立刻拿到交互结果。没有需要应用手动创建/销毁的控件对象，界面结构是应用数据的函数。
- **执行是受控的**：构建函数不按固定帧率运行，只在失效后运行（见 ADR 0006）。
- **状态是保留的**：框架按控件 ID 维护状态存储。悬停/按下/焦点、滚动位置、动画进度、文本光标等交互状态归框架所有，应用不需要自己保存。
- **重型控件是保留节点**：文本编辑、虚拟列表、树、表格在状态存储中拥有长寿命对象，自管排版缓存、行高缓存等，构建时只传入数据视图与配置。
- **布局与绘制有缓存**：构建产出的节点树每帧重建（放在帧竞技场），但文字排版结果、度量结果、可选的子树绘制缓存跨帧保留并按内容哈希校验。
- 不提供通用的保留式控件树 API（没有 `addChild`/`removeChild`/属性绑定）。

## 后果
- 应用代码线性、易读，界面与数据不会失步。
- 构建函数必须是无副作用、可重入的纯声明，否则受控执行（跳帧、同帧二次构建）会暴露错误。这是对应用代码的硬约束，见 06。
- 控件 ID 的稳定性成为正确性的关键，需要明确的 ID 规则与调试期冲突检测。
- 每次失效都重跑整个窗口的构建函数；必须把构建做得足够便宜（见 12 的预算），并用虚拟化避免为不可见内容构建节点。

## 被否方案
- **纯保留模式**：与"受控的即时渲染模式"要求相悖，且应用侧状态同步成本高。
- **纯即时模式（固定帧率）**：空闲耗电，违背被动刷新与性能优先。
- **响应式/虚拟 DOM 差分**：引入一整层运行时与差分算法，掌控度下降。
